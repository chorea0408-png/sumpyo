## 2. 기획 의도

### 무엇을 푸는가
카톡·메모·구글시트에 흩어진 준비 업무를, 세 팀을 병행하는 인도자가 **놓치지 않고 파악**하게 한다.
"할 일 관리"가 목적이 아니라 **"지금 무엇이 막혀 있는지 아는 것"**이 목적이다.

### 차별점 — 왜 아사나/노션이 아닌가
경쟁 축이 두 개다.

| 대상 | 차별 |
|---|---|
| **Praise Hub류** (팀 공유·협업 서비스) | 숨표는 공유가 아니라 **개인의 파악**. 로그인·초대·실시간 협업 없음 |
| **아사나·노션류** (범용 도구) | 숨표만 가진 데이터는 **라인업·팀원·콘티·회고** — 범용 도구가 구조적으로 복제 못 하는 영역 |

**중요한 자기 진단**: 지배적 표면이 체크리스트라 아사나 영역과 겹친다는 위험이 실제로 있었다.
`ServiceNote`(회고)와 `SetlistSong`(콘티)을 넣은 이유가 정확히 그 빈칸을 메우기 위해서다.
**앞으로 기능을 더할 때도 "이게 아사나로 되나?"를 먼저 물을 것.**

### 전략 — Solo Utility First
혼자 써도 가치가 있고, **결과만 카톡에 복사**해서 팀과 만난다.
서버·계정을 만드는 순간 이 철학이 깨지므로, 공유 접점은 전부 "텍스트 복사"로 끝낸다.

현재 복사 접점 3개 — 전부 `lib/share.ts`:
- `summaryText()` — 주간 현황 (홈)
- `noticeText()` — 라인업 공지문 (팀관리 › 라인업)
- `projectSettlementText()` — 프로젝트 정산문 (프로젝트 상세)

### 언어 원칙
죄책감을 주지 않는다. "지연" 대신 **"확인이 필요해요"**, 게임식 점수 대신 **"27번의 예배를 함께 준비했어요"**.
축하는 조용하게. 스트릭(연속 기록)은 **의도적으로 안 만든다** — 한 번 끊기면 벌이 되기 때문.

### 기능 전수

**주간 준비 (코어)**
- 준비팩 12단계 자동 생성 (`WORSHIP_TEMPLATE`) — 이번 주·다음 주는 항상 보장
- 팀별 준비팩 커스터마이징 (`Team.customTemplate`) — 단계 추가/삭제/순서/마감 시각 편집
- 선행 단계 인식 (`STEP_PREREQS`) — 콘티 전엔 공지를 히어로에서 뒤로 미루고 **이유를 표시**(숨기진 않음)
- 대기 상태 (`Task.waiting`) — 누구에게 언제 요청했는지. **공유 텍스트엔 절대 안 들어감**
- 주 경계 이월 (`carriedOver`) — 월요일에 지난주 미완료가 사라지지 않게

**팀 운영 (팀관리 7섹션)**
1. 기본정보 · 2. 팀원&역할 · 3. 라인업 · 4. 준비팩 구성 · 5. 지난 예배 기록 · 6. 팀원 성장 · 7. 예산

- 라인업 로테이션 추천 (`lib/lineup.ts`) — 역할별로 최근에 안 선 사람 우선
- 팀원 성장 (`lib/growth.ts`) — "다은은 싱어 11회, 세컨 0회". **자격 있는데 0회인 역할을 숨기지 않는 게 핵심 가치**(로테이션 사각지대 신호)
- 상시 예산 — 카테고리 4종, 누적 합계만

**장기 프로젝트 ('길게 보기' 모드, 기본 OFF)**
- 프로젝트 + 마일스톤 체크리스트 (팀 무관 독립 목록)
- 프리셋 3종 — 수련회(9) / 소풍·나들이(6) / 특별예배(7)
- 프로젝트 예산 + 카톡 정산문

**공유·내보내기**
- 카톡 텍스트 3종(위 참조) · 공지문 마무리 문구 템플릿 · `.ics` 캘린더 · 백업 JSON export/import
- `scripts/backup-to-report.mjs` — 백업 JSON → CSV 5종 (앱 번들과 무관한 독립 Node 스크립트)

**플랫폼**
- PWA 오프라인 + 새 버전 감지 토스트 · 데스크톱 전용 레이아웃(900px+) · 노치 세이프에어리어

## 4. 데이터 모델

### 엔티티 (`src/types.ts`, 16개)

```
Team ─┬─ TeamMember[]      (한 사람이 여러 역할 겸직)
      ├─ LineupSlot[]?     (없으면 DEFAULT_LINEUP_SLOTS)
      └─ TemplateStep[]?   (없으면 WORSHIP_TEMPLATE)

teamId로 Team을 참조하는 플랫 배열들:
  Task · LineupAssignment · ServiceNote · SetlistSong · Expense

projectId로 Project를 참조하는 플랫 배열들:
  ProjectMilestone · ProjectExpense

어디에도 안 묶인 것:
  Profile · NoticeClosingTemplate
```

### 핵심 설계 원칙 — **"스코프가 다르면 별도 엔티티"**
이 프로젝트에서 가장 많이 반복된 판단이고, 매번 옳았다.

- `ServiceNote`가 `Task`의 필드가 아닌 이유: '마침 기록' 업무는 지울 수 있는데 **회고가 함께 사라지면 안 된다**
- `Project`가 `Task`에 안 얹힌 이유: 얹으면 **5곳이 동시에 깨진다** — PriorityCarousel 인덱스, `isTask()`가 `teamId` 필수라 **백업 전체 실패**, `deleteTeam` 연쇄 삭제, CalendarGrid 요일 게이트, `order`/`due` 필수(마일스톤은 날짜 미정이 정상)
- `ProjectExpense`가 `Expense` 재사용이 아닌 이유: `Expense.teamId`를 옵셔널화하면 백업 가드·필터·`deleteTeam` 세 곳의 불변식이 흔들림

**→ 새 개념이 생기면 기존 타입에 필드를 얹기 전에 위 목록을 먼저 확인할 것.**

## 5. 아키텍처

### 스택
React 18 + TypeScript + Vite 5 · **런타임 의존성은 react/react-dom 둘뿐** · 상태관리 라이브러리 없음 · 백엔드 없음 · 테스트 러너 없음

### 폴더
```
src/
  App.tsx        888줄 — 상태·라우팅·CRUD 핸들러 전부
  types.ts       엔티티 정의 (단일 소스)
  index.css      3,100줄 — 전역 단일 스타일시트
  components/    41개 — 전부 프레젠테이션 (자체 영속화 없음)
  lib/           13개 — 순수 로직 + 훅 2개
  data/          7개 — 정적 목록 + 시드
scripts/         백업→CSV 변환 (독립)
```

### 상태 관리 — "App.tsx 단일 소유"
컴포넌트는 상태를 **소유하지 않는다**. `useState` 26개가 전부 `App.tsx`에 있고 props로 내려간다.

영속화 패턴은 예외 없이 동일:
```tsx
const [x, setX] = useState(() => storage.loadX());
useEffect(() => storage.saveX(x), [x]);
```

**이 구조를 유지하는 이유**: 백업/복원·데모 초기화·랜딩 "새로 시작" 세 경로가 **모든 배열을 한 번에** 갈아끼워야 한다. 상태가 흩어지면 이 세 곳이 조용히 깨진다.
**대가**: `App.tsx`가 888줄이고 prop drilling이 깊다. 지금 규모에선 감당 가능하지만, 엔티티가 더 늘면 Context 도입을 검토할 지점.

### 레이어 규칙
```
data/ (정적)  →  lib/ (순수 함수)  →  components/ (표시)
                       ↑
                   App.tsx (상태·조립)
```
`lib/`은 React를 모른다(훅 2개 제외). 날짜·우선순위·통계·공유 텍스트 전부 순수 함수라 추론이 쉽다.

### ⚠️ 데스크톱 블록이 둘로 나뉜 이유 — 이 프로젝트 최대의 함정
캘린더·통계·마이페이지·팀관리의 **기본(모바일) 선언이 블록 1보다 파일 뒤쪽**에 있다.
같은 명시도면 소스 순서상 뒤가 이기므로, 그 선택자를 블록 1에 쓰면 **조용히 무효화된다.**

**규칙**:
- 새 데스크톱 규칙을 추가할 땐 그 선택자의 기본 선언 위치를 `grep -n '^\.selector' src/index.css`로 먼저 확인
- 기본 선언이 1290행보다 뒤에 있으면 → **꼬리 블록(2927행~)에 쓸 것**
- 실제로 이 함정 때문에 하단 탭바가 데스크톱에서 모바일 모양으로 보이는 버그가 났었다

| 시트 | 바텀시트 88dvh | 중앙 모달 560px |

## 7. 확립된 코드 관례

### 새 엔티티를 추가하는 절차 (S5·S7·S2·S4에서 4번 반복해 굳어짐)
1. `types.ts`에 인터페이스
2. `storage.ts`에 `const K_X` + `loadX`/`saveX` + (데이터면) `clearData()`에 추가
3. `backup.ts`에 4곳 — `BackupFile` 필드 / `exportBackup` 트레일링 파라미터 / `ImportResult` / `isX()` 가드 + **관용적 `.filter(isX)` 파싱**
4. `App.tsx`에 state + effect + CRUD 핸들러
5. `MyPage.tsx`의 export 버튼·`onImport` 시그니처에 트레일링 인자 스레딩

### 🔴 백업 파싱은 반드시 `.filter()`, 절대 `.every()` 아님
`.every()`면 **한 줄만 깨져도 팀·업무 전체가 복원 불가**가 된다.
`teams`/`tasks`만 엄격 검사(`.every`)하고 나머지 신규 배열은 전부 관용적으로 거른다. 매번 깨진 행 섞어서 검증할 것.

### 배열 소유권 — `onChange(전체배열)` vs 전용 핸들러
- 엔티티에 `teamId`/`projectId`가 **없으면** (예: `NoticeClosingTemplate`) → 자식이 `onChange(전체배열)`로 통째 교체해도 안전
- 엔티티에 스코프 키가 **있으면** (예: `Expense`) → **전용 핸들러**(`addExpense`/`removeExpense`) 사용. 팀 화면에서 전체 배열을 교체하면 다른 팀 데이터를 날릴 수 있다

### `window.confirm`은 자식이 소유
호출하는 자식 컴포넌트에만 둔다. `App.tsx` 핸들러에도 넣으면 **이중 확인**이 된다 (S2에서 실제로 냈다가 고침).

### 날짜 — UTC 파싱 우회
- 입력값: `toDateInput(d)` (`lib/date.ts`, 로컬 기준 yyyy-mm-dd)
- 저장된 date-only 문자열 파싱: `` new Date(`${dateStr}T00:00:00`) `` — **`Z` 없이** 로컬 강제
- `new Date('2026-07-28')`은 UTC 자정이라 KST에서 **하루 밀린다**
- "미래" 판정은 반드시 `startOfDay(now)` 기준 (`nextServiceOn()`으로 통합해둠)

### CSS 재사용 우선
새 클래스를 만들기 전에 기존 것을 찾는다. 실제로 S4·S6는 **신규 CSS 0줄**, S3도 0줄로 끝났다.
주요 재사용 자산: `.filter-chip`(단일선택 — `type="radio"`는 코드베이스 전체 0건) · `.template-*`/`.tmpl-*`(카드 리스트+순서이동+삭제) · `.expense-*` · `.tm-section`/`.tm-section-label`(접힘 헤더) · `.cal-month`(접힘 위젯) · `.overlay`/`.sheet`(바텀시트)

### 터치 타겟
44px 이상. 시각 크기를 바꾸기 싫으면 `::after { position:absolute; inset:-Npx }`로 히트 영역만 확장.
**단 인접 형제와 겹치면 안 되므로 방향별로 다르게** 줄 것.

## 8. 알려진 함정 (실제로 당한 것만)

| 함정 | 증상 | 대응 |
|---|---|---|
| **PWA 서비스워커 캐시** | 배포해도 옛 화면. 네트워크는 200이라 눈치 못 챔 | 검증 전 `navigator.serviceWorker.getRegistrations()` 해제 + `caches.keys()` 삭제. `registerType:'prompt'` + 갱신 토스트로 완화해둠 |
| **CSS 캐스케이드** | 데스크톱 규칙이 조용히 무효화 | §6 참조 |
| **Vite base 경로** | 라이브에서만 404 | JSX 문자열의 public 자산은 반드시 `${import.meta.env.BASE_URL}파일명` |
| **클릭 직후 같은 스크립트에서 상태 읽기** | 갱신 전 값을 읽고 "버그"로 오인 | 브라우저 자동화에서 클릭과 확인을 **별도 호출**로 분리 |
| **`position:fixed` 스크린샷** | 스크롤 중 합성 위치가 실제와 다름 | `getBoundingClientRect()`로 교차 검증 (도구 이슈, 제품 버그 아님) |
| **`monthKey()`** | `2026-0` = 1월 (0-based, zero-pad 없음) | Map 키로만. 렌더·사전순 정렬 금지 |
| **팀관리 아코디언 확장** | N번째 head가 auto-placement로 밀림 | 섹션 추가 시 꼬리 블록의 `repeat(N,...)`과 `nth-of-type(N)`을 **함께** 증가 (삭제 버튼은 자동) |
| **StrictMode 이중 실행** | setState effect가 두 번 | 함수형 업데이터 안에서 최신 상태 재확인 |
| **CSS 클래스 축 바꿔 재사용** | 크기가 엉뚱하게 나옴 | 가로 flex용 클래스(`flex: 1 1 160px`)를 세로 컬럼에 재사용하면 `flex-basis`가 **높이**로 적용된다 |
| **`min-width: 0` 누락** | 페이지 전체가 가로로 밀림 | scroll-snap 캐러셀은 **부모 체인 전체**에 `min-width: 0`이 필요 |
| **바텀시트 `autoFocus`** | iOS에서 확대 + 스크롤 꼬임 | 시트 등장 애니메이션과 키보드가 동시에 뜨면 깨짐 → **지연 포커스**(200ms)로 전환 |
| **데모 데이터에 라인업 이력 0건** | S6 분기 테스트 불가 | 시드는 Task 완료 기반이지 라인업 확정 기반이 아님. `sumpyo.lineup.v1`에 과거 레코드 수동 주입 필요 |

## 9. 명시적으로 안 하는 것

### 넘지 않는 선 (설계 원칙)
- 프로젝트/마일스톤을 **공유 캘린더에 그리지 않는다**
- 마일스톤을 `weekTasks`·`pending`·완료 로직에 **합치지 않는다**
- `summaryText()`에 프로젝트·예산 줄을 **넣지 않는다**
- 대기 상태(누가 며칠째 답 없는지)는 **어떤 공유 텍스트에도 안 들어간다** — 개인 파악용
- 예산은 **개인별 잔액·미정산 상태를 만들지 않는다** — 만드는 순간 계정이 필요해진다
- 스트릭(연속 기록)을 만들지 않는다

### 사용자가 거부한 항목 (다시 제안하지 말 것)
분석/피드백 채널 연동 · 여러 성경 번역본 선택 · 팀 순서 직접 정렬 · 다크 모드 · 리마인더 알림 · 라인업 공지문 전체 자유 템플릿

### MVP 범위 밖
로그인 · 서버 · 팀원 초대 · 실시간 협업 · 악보 뷰어 · AI · 커뮤니티 · 푸시 알림
(악보·음원은 저작권 문제로 **외부 링크만** 취급)

> ※ 초기 README는 '회계'도 제외 목록에 뒀지만, 예산·정산문(S4/S5)을 출하하면서 **철회됨**.
> 단 위의 "개인별 잔액 안 만듦" 선은 유지된다.

## 11. 개발 히스토리

39커밋의 흐름. **매번 "무엇을 더할까"가 아니라 "무엇이 안 맞나"에서 출발**했다는 게 이 프로젝트의 리듬이다.

| 단계 | 한 일 | 계기 |
|---|---|---|
| **MVP** | 주간 준비 대시보드 코어 (`bdebfec`) | 부트캠프 미니 프로젝트 |
| **기능 확장** | 랜딩·예배 추가·준비팩·캘린더·마이페이지·PWA | 발표 준비 |
| **데이터 모델 확장** | 팀원·역할·라인업·팀별 템플릿 | "팀원이 없으면 라인업을 못 짠다" |
| **연결** | 라인업↔체크리스트↔공지문, `.ics`, 백업→CSV | 흩어진 기능을 하나의 흐름으로 |
| **Stage 0-1** | Explore 3개로 전수 점검 → 실버그 수정 + UX 일관성 | 기능이 아니라 **품질** 라운드 |
| **마이페이지 고도화** | 라인업 히스토리·준비 통계·서명·사용 안내 | "마이페이지가 부실하다"는 피드백 |
| **G1~G7** | 발표 자료의 5가지 질문·5가지 원칙을 코드와 1:1 대조 → 갭 메움 | **5개 질문 중 3개가 구조적으로 답 불가**였음 |
| **Stage 2** | 데스크톱 레이아웃 전면 (4커밋: 캘린더·네비·마이페이지·팀관리) | 모바일 전용이라 넓은 화면이 텅 빔 |
| **S7→S6→S5→S1+S2→S4** | ‘길게 보기’ 백로그를 **역순**(의존성 없는 것부터)으로 | 큰 기능을 작게 쪼개 매번 출하 가능하게 |
| **S3 + M1~M3** | 프리셋 + 모바일 버그·구조 정리 | 데스크톱만 챙기다 모바일이 밀렸음 |

**G1~G7이 특히 중요한 라운드였다.** 발표에서 “이런 질문에 답하는 서비스”라고 말해놓고
실제로는 데이터 모델에 그 개념이 아예 없던 것들(대기 상태·회고·콘티·단계 키)을 그때 메웠다.
`ServiceNote`·`SetlistSong`·`Task.waiting`·`Task.stepKey`가 전부 이 라운드 산물이다.
